# Scrinium v0.2: Evidence-Backed Project Knowledge Architecture

Status: implemented v0.2 core; protected architecture overview acceptance remains an owner-governed draft decision

Supported Go baseline: Go 1.27.0 or newer within the Go 1 compatibility contract. CI and release workflows select the repository-declared Go 1.27 toolchain.

Assessment date: 2026-08-20

Scope: v0.2 architecture, migration plan, and implemented-boundary notes

## Executive decision

Scrinium v0.2 should manage durable project claims and the evidence used to assess them. A Markdown page remains useful as a document or human view, but its presence in `llm-wiki/` must not imply that its contents are correct.

The canonical v0.2 knowledge record should be one deterministic JSON file per claim under `llm-wiki/claims/`. Markdown remains readable and can cite claim IDs, source IDs, decisions, files, and validation results. It is not the canonical machine representation of claim state.

Claim state should not be one flat enum. `superseded`, `stale`, `verified`, and `contradicted` describe different dimensions. v0.2 should represent:

- lifecycle: `active`, `superseded`, or `withdrawn`;
- assessment: derived as `asserted`, `sourced`, `observed`, `verified`, or `challenged`;
- freshness: derived as `current`, `stale`, or `unknown`;
- each validation attempt: `pass`, `fail`, or `cannot_evaluate`.

This design deliberately makes `verified` difficult to obtain and easy to lose. It is always scoped to named validation bindings, validator versions, evidence fingerprints, and a repository revision. A failed or unavailable re-check cannot preserve an unqualified current-verified presentation.

## 1. Current-state architecture

Scrinium v0.1.3 is a standard-library Go program with a thin executable entry point and almost all behavior in one package.

```text
main.go
  -> CLI selector or stdio MCP server
       -> cmd/scrinium.App
            -> JSON-RPC decode/dispatch/MCP response shaping
            -> tool definitions and handlers
            -> session bookkeeping
            -> write-governance decisions
            -> path resolution and filesystem writes
            -> wiki setup, page operations, source registration
            -> lint/adoption reports

cmd/scrinium/cli.go
  -> agent-instruction generation
  -> one-process wrapper around individual MCP tool handlers

scrinium.json
  -> wiki root and protected path patterns

llm-wiki/
  -> Markdown pages, source registry, source summaries, workflows, and log
```

Specific implementation points:

- `main.go:15-39` chooses a CLI subcommand or creates one `App` and runs JSON-RPC over stdio.
- `cmd/scrinium/app.go:18-23` makes `App` the owner of configuration, wiki root, transport-facing behavior, and session state.
- `cmd/scrinium/app.go` loads configuration and creates the wiki root; opening the service writes nothing into the wiki. `scrinium-guide.md` is a `setup_llm_wiki` artifact like every other standard page — discovery operations (including `capabilities`) are read-only toward the wiki.
- `cmd/scrinium/app.go:324-379` scans newline-delimited JSON-RPC requests from process stdin and writes responses to process stdout.
- `cmd/scrinium/app.go:381-418` dispatches protocol methods; `app.go:435-629` declares the MCP tool surface; `app.go:752-801` dispatches tool names.
- `cmd/scrinium/app.go:804-1269` implements page, draft, log, session, lint, source, create, move, and archive operations directly against the filesystem.
- `cmd/scrinium/app.go:1271-1369` maintains a single in-memory `SessionState` attached to the `App`.
- `cmd/scrinium/app.go:1543-1595` evaluates protected path patterns; `app.go:1855-1914` confines requested paths to the configured wiki root; `app.go:1920-1949` provides single-file atomic replacement.
- `cmd/scrinium/app.go:1597-1723` implements lint and its prompt-injection phrase scan.
- `cmd/scrinium/app.go:1749-1814` renders source-summary Markdown and modifies the Markdown source registry with substring operations.
- `cmd/scrinium/cli.go:284-342` generates managed instruction blocks; `cli.go:348-447` creates a fresh `App` for each direct MCP-tool CLI invocation.

The current persistent knowledge model is therefore implicit. Page paths, Markdown headings, frontmatter, source IDs, prose conventions, and log entries carry meaning, but there is no parsed `Claim`, `Evidence`, or `ValidationResult` domain object.

## 2. Specific weaknesses found in current code

### 2.1 `app.go` has too many responsibilities

`cmd/scrinium/app.go` is 1,964 lines and contains protocol types, tool schemas, request dispatch, MCP response formatting, config loading, wiki templates, application workflows, session policy, filesystem operations, governance, source-registry editing, and linting. The code graph identifies `buildWikiLintReport` as the repository's highest-complexity function.

The practical problem is not file length by itself. Domain operations return MCP-shaped `map[string]any` values and parse `map[string]any` arguments, so tests and future transports must work through transport concepts. Storage, authorization, and semantic state cannot evolve independently.

### 2.2 MCP transport and domain logic are coupled

`handleToolCall` selects domain behavior, while each selected handler both performs the operation and constructs MCP content. JSON-RPC error policy is embedded in `dispatch`. The direct CLI deliberately reuses the MCP handler by manufacturing a JSON-RPC-shaped request (`cli.go:399-414`).

Consequences:

- there is no transport-independent application service to test;
- adding a non-MCP caller requires MCP parameter and response conventions;
- typed validation errors, governance denials, missing evidence, and operational failures collapse into strings;
- tool schemas can drift from handler expectations because both are handwritten in separate sections of the same file.

### 2.3 `SessionState` is in memory and is not a session identity

`SessionState` is a pointer on one `App`. It has no ID, owner/client identity, repository revision, persistence, locking, or recovery. Calling `begin_session` replaces any existing session without warning. Multiple logical clients sharing an `App` would share and overwrite the same state.

Within one long-running stdio process, the bookkeeping can require certain reads before MCP-mediated writes. It cannot observe arbitrary repository edits, so it does not enforce the complete project workflow described by generated instructions.

### 2.4 Session-oriented CLI commands do not compose across processes

Every direct CLI invocation creates a new `App` (`cli.go:392-398`). A source-tree smoke check on 2026-08-20 produced:

```text
$ go run . begin_session --repo .
Started LLM Wiki session...
$ go run . session_status --repo .
{"active":false,...}
```

As a result, `begin_session`, page reads, page writes, `session_status`, and `finish_session` cannot form a workflow across normal separate CLI processes. The current CLI test covers `capabilities`, one read, and a missing-config error, but not a cross-process session (`app_test.go:1236-1298`).

### 2.5 Write governance and path safety are useful but narrower than advertised

Worth preserving:

- logical `..` traversal and existing symlink escapes are rejected;
- a non-existent target's nearest existing parent is resolved before use;
- normal page replacement uses a same-directory temporary file and rename;
- protected writes receive actionable errors;
- create and move operations refuse accidental overwrite.

Limits and defects:

- the configured `wiki_root` is not required to remain inside the repository containing `scrinium.json`; `../` configuration can select another local tree;
- path validation and the eventual filesystem operation are separate, leaving a local time-of-check/time-of-use window if a directory is swapped concurrently;
- file type is not constrained: page tools and resource listing can address non-Markdown files and some operations can address directories;
- invalid protected glob patterns are silently treated as non-matches because `filepath.Match` errors are discarded;
- `append_log` may modify any file under a directory-pattern protection, including `architecture/*`, not only declared append-only records;
- `setup_llm_wiki` and the `NewApp` guide bootstrap write without session bookkeeping or ordinary write-governance checks;
- source registration updates two files without a transaction or lock, so a partial write or concurrent update can leave summary and registry inconsistent;
- write governance is application policy, not filesystem access control. Direct filesystem writers bypass it, as the generated enforcement block itself acknowledges.

v0.2 must describe these controls as scoped write governance and repository path confinement, not as a general authorization boundary.

### 2.6 The source registry records provenance but does not establish truth

The current registry is a manually structured Markdown document. `register_source`:

- performs only a weak prefix/path-separator check on source IDs;
- does not verify the claimed raw file exists or is a regular repository-owned file;
- does not hash or otherwise identify the source bytes;
- accepts arbitrary trust levels and date strings;
- does not enforce raw-source immutability;
- creates a summary with pending placeholders;
- finds and replaces registry entries through substring matching.

The source registry is valuable provenance infrastructure, but a registered source and an LLM-authored summary are not evidence that every derivative statement is correct. `trusted-owner` identifies origin; it must not become a numeric confidence score or an automatic truth designation.

### 2.7 Current lint behavior is materially narrower than README claims

The README says lint scans contradictions, stale claims, missing indices, and prompt-injection vectors. `buildWikiLintReport` actually checks:

- presence of template-defined standard files;
- literal occurrence of each page path in `index.md`;
- whether files under `sources/` contain the words `Source ID` or `source ID`;
- whether any Markdown file contains one of six instruction-like phrases.

It does not parse claims, compare propositions, detect semantic contradictions, evaluate staleness, validate general provenance, parse log coverage, distinguish important from unimportant orphans, find duplicates, or verify cross-references. `handleLintLLMWiki` calls the routine deterministic even though one check is a content heuristic.

Running current source against the repository reports a high `source_instruction_risk` for `security/untrusted-sources.md` itself and a missing-source-metadata warning for `sources/README.md`. These are false positives caused by scanning trusted guidance and treating a directory README as a source summary.

### 2.8 The prompt-injection check is a phrase heuristic

`sourceInstructionRisk` lowercases an entire Markdown file and searches for six substrings. It has no provenance boundary, quoting awareness, Markdown structure, source classification, allowlist, contextual analysis, or confidence explanation. It is useful only as a review lead over untrusted source-derived content. It must be labeled heuristic and must never change claim state automatically.

### 2.9 “LLM wiki as source of truth” is an unsafe abstraction

The README, generated `AGENTS.md`/`CLAUDE.md` block, and wiki index describe `llm-wiki/` as persistent memory or a source of truth and claim it reduces hallucinations. Current storage proves only that text was stored. A page can be wrong, stale, internally inconsistent, malicious, or generated from a misunderstood source.

The v0.2 replacement is: Scrinium is the repository-owned record of project claims, their provenance, and their bounded validation history. It does not make a claim true by storing it.

### 2.10 `AGENTS.md` and `CLAUDE.md` provide guidance, not enforcement

The generator usefully preserves user content outside marker blocks, is idempotent, supports dry-run/check, and documents that direct filesystem changes are invisible. However:

- it cannot compel an agent or nonparticipating tool to call Scrinium;
- the command name `enforce-agents` overstates the mechanism;
- generated text tells agents to treat the wiki as the source of truth;
- generated config embeds an absolute machine-specific path;
- `--check` is not run by current CI;
- selected agent names affect descriptive text, but the generator still produces both `AGENTS.md` and `CLAUDE.md`.

For v0.2, preserve managed-block generation but rename its promise to instruction synchronization. Keep `enforce-agents` temporarily as a deprecated alias if compatibility is required.

### 2.11 Tests and CI cover important units but miss system boundaries

There are 51 tests in one `cmd/scrinium/app_test.go`. They cover page operations, basic MCP dispatch, protected paths, common traversal attempts, symlink-parent rejection, setup idempotence, in-process session obligations, source registration, managed-block generation, and a small direct-CLI surface. `make test` passed on 2026-08-20.

Important gaps include:

- no stdio `Run` protocol test, scanner limit test, notification test, or MCP conformance test;
- no cross-process session workflow test;
- no concurrent writer, partial source-registration, or race test;
- no malformed/invalid governance pattern tests;
- no repository-root confinement test for `wiki_root`;
- no claim/evidence/state tests because those types do not exist;
- lint tests assert only that missing-page/path strings appear, not the advertised behaviors;
- no tests for prompt-injection false positives or scope;
- no migration or compatibility fixtures over real existing Markdown.

The only GitHub Actions workflow is a tag-triggered GoReleaser job. There is no pull-request or branch CI job that runs `make verify`, agent-guidance `--check`, tests, static analysis, or vulnerability checks before merge.

### 2.12 Required-page references are not deterministically validated

Root `AGENTS.md` and `llm-wiki/index.md` now consistently identify the existing `platform/open-source.md` as the startup/platform document. That consistency still depends on manual maintenance. v0.2 should make required-page references deterministically lintable so missing or conflicting startup paths are reported before project work.

## 3. v0.2 goals

1. Make `Claim`, not `Page`, the primary durable knowledge object.
2. Record why a claim is held through explicit, independently addressable evidence metadata.
3. Separate authorship, evidence origin, validation outcome, claim assessment, lifecycle, and freshness.
4. Derive confidence-related presentation from checkable records; never accept a caller-written `verified` label without satisfying policy.
5. Degrade toward uncertainty when evidence, validators, source bytes, bindings, or repository revisions cannot be checked.
6. Keep project knowledge local-first, repository-owned, Git-diffable, human-readable, and usable without a database, daemon, network, or cloud service.
7. Keep the core independent of Gograph and Rulefloor internals through a generic validation boundary.
8. Separate transport, application orchestration, storage, governance, knowledge model, validation, lint, sessions, and optional integrations.
9. Preserve useful v0.1 behavior through typed internal adapters and explicit deprecation rather than a rewrite.
10. Make every deterministic claim made by Scrinium testable; label every heuristic output as heuristic.

## 4. Non-goals

- Implementing Gograph or Rulefloor adapters in v0.2's first claim-model slice.
- Proving arbitrary natural-language statements true or false.
- Automatically extracting authoritative claims from every Markdown sentence.
- Building a semantic contradiction engine from prose.
- Requiring a database, background server, hosted account, or network service.
- Replacing Git history, ADRs, source code, tests, issue trackers, or human review.
- Turning owner trust into a universal truth score.
- Making sessions a security sandbox or a guarantee that an external agent followed instructions.
- Rewriting all existing Markdown or removing page tools in one release.
- Treating a Gograph relationship as proof of runtime behavior or a Rulefloor pass as proof beyond its bound invariant.

## 5. Trust model

### 5.1 Trust is scoped, not scalar

Scrinium should not store one `confidence` number. Evidence authority depends on the proposition:

- an owner assertion can be authoritative about desired policy but not about deployed behavior;
- an accepted ADR supports what was decided, not whether code still implements it;
- a repository reference proves that bytes existed at a path/revision, not that a prose interpretation is correct;
- a structural analyzer can support code-shape claims within its analysis limits, not runtime guarantees;
- an executable invariant can verify only the exact bound property for the recorded inputs and revision.

Trust metadata records origin, scope, and method. Admission policy determines whether that evidence is suitable for a particular claim and assessment level.

### 5.2 Required distinctions

| Concept | Meaning | What it does not mean |
| --- | --- | --- |
| Stored | A record parses and exists in the repository | Correct, supported, or current |
| Asserted | Someone or some process recorded a claim, with no admissible independent support | False, but also not corroborated |
| Sourced | At least one traceable, available documentary/assertion source supports it | Verified against implementation |
| Machine-observed | A named validator observed a condition for recorded inputs/revision | Proof of an invariant or all executions |
| Machine-verified | A verification-grade validator passed an explicit required binding for recorded inputs/revision | Global correctness beyond that binding |

### 5.3 Trust rules

1. Claim authorship is provenance, not supporting evidence.
2. An LLM-generated summary cannot cite itself, its containing page, or another derivative of the same generation as evidence for its own correctness.
3. A derivative may cite independent upstream evidence and must preserve its provenance lineage.
4. Multiple references derived from the same source are not independent corroboration.
5. Evidence has a polarity (`supports`, `challenges`, or `context`) and a scope. Context evidence cannot raise assessment.
6. Evidence availability and content identity must be checked separately from its semantic relevance.
7. Successful validation is bounded by validator identity/version, binding, repository snapshot, input fingerprint, and time/freshness policy.
8. Missing, expired, changed, or unresolvable evidence never silently retains current verification.
9. Conflicting evidence creates a reviewable challenged state; Scrinium does not silently select a winner.
10. Heuristics may create findings, never evidence or state transitions.

## 6. Claim model

### 6.1 Claim aggregate

A claim is a durable assertion with stable identity. The minimum canonical fields are:

- `schema_version`: versioned record schema;
- `id`: stable repository-unique identifier;
- `subject`: stable topic or project subject;
- `statement`: one testable or reviewable assertion, not a multi-paragraph summary;
- `lifecycle`: owner-authored lifecycle state and optional supersession links;
- `authorship`: who or what created the record and when;
- `evidence`: evidence records or references, each with identity, polarity, scope, origin, and locator;
- `validation_policy`: named bindings required to reach a verification assessment;
- `validation_results`: append-preserving result records tied to bindings and input fingerprints;
- `created_at` and `updated_at`.

`last_validated` and the displayed assessment should be derived, not independently editable fields. A human view may render them for convenience.

### 6.2 State model

A single state list mixing `asserted`, `verified`, `stale`, `contradicted`, and `superseded` is rejected because those values are not mutually exclusive.

**Lifecycle** is explicitly changed by an authorized claim edit:

- `active`: the assertion is part of current project knowledge;
- `superseded`: a newer claim replaces it; `superseded_by` is required;
- `withdrawn`: the assertion was retracted without a replacement; a rationale is required.

**Assessment** is derived from admissible, available evidence and validation records:

- `asserted`: no admissible independent supporting evidence;
- `sourced`: documentary, decision, owner/human assertion, external source, or repository-reference evidence supports the claim, but no current validation raises it further;
- `observed`: at least one current observation-grade check supports the claim, but the verification policy is not satisfied;
- `verified`: every required verification binding passes, results are current, referenced evidence is available, and no current required binding fails;
- `challenged`: a current required validation fails or explicit admissible challenge evidence exists. This name is preferred to `contradicted` because a failed tool or competing document is not automatically a logical proof of negation.

**Freshness** is independently derived:

- `current`: all evidence/results needed for the displayed assessment still match their declared revision, fingerprint, and validity policy;
- `stale`: previously usable evidence/result expired, changed, disappeared, lost its validator, or no longer matches the repository snapshot;
- `unknown`: freshness has never been checked or cannot be determined.

Examples of valid combinations include `active / sourced / stale`, `active / challenged / current`, and `superseded / verified / stale`. Human views should lead with lifecycle, then assessment and freshness; they must not flatten these into a misleading single word.

### 6.3 Validation outcomes are not claim states

Each attempt records exactly one outcome:

- `pass`: the bound predicate held within the validator's declared scope;
- `fail`: the bound predicate did not hold within that scope;
- `cannot_evaluate`: the check could not produce a trustworthy yes/no result.

Timeout, cancellation, missing executable, unsupported binding version, missing artifact, stale analyzer index, parse failure, and unavailable evidence all yield `cannot_evaluate` with a machine-readable reason. They never yield `pass` and never preserve `freshness: current` for a prior pass.

## 7. Evidence model

Evidence is a typed record about why a claim is supported or challenged. Each evidence item needs a stable ID, kind, polarity, locator, provenance lineage, scope, capture time when applicable, and availability/content identity when checkable.

| Evidence kind | Appropriate use | Insufficient by itself |
| --- | --- | --- |
| `owner_assertion` / `human_assertion` | Intent, policy choice, reported project fact with named provenance | Implemented or runtime behavior |
| `decision` | Accepted ADR/design decision and its status | Current code conformance |
| `external_source` | Dependency, standard, external system, or background facts | Facts about this repository unless connected explicitly |
| `repository_reference` | Path, symbol, range, revision, and content digest | Semantic interpretation or runtime behavior |
| `manual_verification` | Recorded procedure, actor, time, inputs, and result | Reproducible machine proof unless policy explicitly accepts it |
| `validator_observation` | Machine-observed structure or behavior for a snapshot | Verification-grade proof |
| `validator_proof` | Successful executable proof binding within declared scope | Any property outside the binding |

Evidence should also record:

- `polarity`: `supports`, `challenges`, or `context`;
- `origin`: owner, person, repository, external source, or validator identity/version;
- `locator`: a typed scheme such as `source:`, `adr:`, `repo:`, `manual:`, or `validation:`;
- `scope`: what part of the statement the item bears on;
- `fingerprint`: source digest, repository revision/tree digest, or validator input digest when available;
- `captured_at` and optional `valid_until`;
- `derived_from`: upstream evidence IDs to expose common-origin duplication.

Evidence admission is claim- and policy-specific. Merely adding more evidence records must not monotonically increase confidence.

## 8. Validation model

### 8.1 Generic boundary

The validator boundary should be typed, context-aware, transport-independent, read-only with respect to the knowledge store, and generic over external systems. A suitable Go shape is:

```go
type Validator interface {
	Descriptor() Descriptor
	Validate(ctx context.Context, req Request) (Result, error)
}

type Request struct {
	Claim      knowledge.Claim
	Binding    knowledge.ValidationBinding
	Repository RepositorySnapshot
}

type Result struct {
	Outcome         Outcome // pass, fail, cannot_evaluate
	Assurance       Assurance // observation or verification
	Reason          string
	Evidence        []knowledge.Evidence
	InputFingerprint string
	StartedAt       time.Time
	CompletedAt     time.Time
}
```

Names may change during implementation, but these boundaries are required:

- `Descriptor` supplies stable validator ID, version, supported binding versions, and maximum assurance. A result cannot claim assurance above its registered descriptor.
- `ValidationBinding` is generic (`validator`, binding schema/version, reference, and validated parameters). The knowledge core contains no Gograph or Rulefloor types.
- `RepositorySnapshot` identifies a confined repository root and revision/content fingerprint. Validators do not infer which repository was intended.
- validators return facts/results and do not mutate claims, evidence files, sessions, or Markdown;
- the orchestration service converts returned evidence into a persisted result, recomputes assessment/freshness, and writes atomically;
- an expected inability to check returns `cannot_evaluate`; an unexpected Go error is also converted by the orchestrator into a persisted `cannot_evaluate` diagnostic. Context cancellation/deadline is never ignored.

### 8.2 Validation policy

`verified` must require an explicit policy. The default for a claim with no policy is never verified. A policy names required bindings and combination mode; v0.2 should support only `all_required` to avoid speculative Boolean policy languages.

Observation-grade validators can produce `observed` but cannot satisfy a verification-grade binding. Manual validation is observation-grade by default. Whether an owner may explicitly authorize a particular manual binding as verification-grade is an owner policy decision listed below.

### 8.3 Result history

Do not overwrite the last result without trace. Retain bounded recent history or append result records with stable IDs, while designating the latest result per binding deterministically. Repository churn can be controlled later through an explicit retention rule. A prior pass remains historical evidence after a re-check becomes unavailable, but freshness becomes stale and the current assessment falls below verified.

## 9. Proposed package boundaries

Do not mechanically create every package named in the prompt. The repository is small, and splitting `claims` and `evidence` into mutually dependent micro-packages immediately would add ceremony. The following boundaries follow current responsibilities and dependency direction:

```text
cmd/scrinium/
  executable wiring and flag definitions only

internal/mcp/
  stdio JSON-RPC transport, MCP schemas, request/response adapters

internal/app/
  transport-independent use cases and transaction orchestration

internal/knowledge/
  Claim, Evidence, ValidationBinding/record, lifecycle and derived-state rules

internal/store/
  repository root, document compatibility store, JSON claim store,
  atomic writes, locking, path/file constraints, schema-version dispatch

internal/governance/
  typed operations and policy decisions over normalized repository-relative targets

internal/session/
  durable work-session records, IDs, lifecycle, and completion checklist policy

internal/validation/
  Validator interface, registry, orchestration, freshness and result admission

internal/lint/
  deterministic integrity rules and explicitly separate heuristic analyzers

internal/integrations/gograph/   # implemented structural-validator CLI adapter
internal/integrations/rulefloor/ # implemented invariant-validator CLI adapter
```

Dependency direction:

```text
mcp and cmd -> app -> knowledge + store + governance + session + validation + lint
store/governance/session/lint/validation -> knowledge where needed
integrations -> validation + knowledge
knowledge -> Go standard library only; no transport, filesystem, or integration imports
```

`internal/store` should own rooted filesystem primitives so every caller gets the same path, symlink, regular-file, locking, and atomic-write policy. `internal/governance` decides whether an operation is permitted; it must not implement filesystem traversal. `internal/app` is the only layer that sequences multi-record operations.

## 10. Storage format decision and rejected alternatives

### Decision: dedicated, one-record-per-claim JSON registry

Choose option B, implemented as a directory registry rather than one monolithic file:

```text
llm-wiki/
  claims/
    AUTH-ADMIN-LOCAL-1.json
    ...
  ...existing Markdown...
```

The claim JSON is canonical. Pretty-printed Markdown is a human view or narrative document and may reference claim IDs. The directory is the registry; a generated index may accelerate navigation but must be disposable and non-authoritative.

Reasons:

- parsing reliability: Go's standard `encoding/json` gives strict, versionable parsing without a new dependency or a hand-rolled YAML parser;
- merge behavior: one claim per file localizes conflicts; a monolithic array would make unrelated claims collide;
- human readability: pretty JSON with stable struct field order, two-space indentation, and a final newline is reviewable in Git;
- agent usability: agents can read or edit one complete typed record without parsing a large Markdown document;
- migration cost: existing Markdown can remain untouched and gain claim references gradually;
- maintenance: schema versions, strict enum/date/ID checks, and deterministic serialization are straightforward;
- locality: all canonical knowledge remains repository-owned and usable without a service or database.

Canonical writers must reject unknown schema versions, duplicate JSON keys, unknown fields unless a migration explicitly allows them, filename/ID mismatch, unsafe IDs, invalid timestamps/enums, and non-regular or linked claim files. Writes should use stable formatting and compare-before-replace to avoid no-op diffs.

Evidence and validation records should be embedded in the claim aggregate for v0.2. Most validation results are claim-specific, and this permits one atomic write. Shared upstream artifacts remain referenced by stable source/ADR/repository locators rather than copied. A separate global evidence database is premature and creates cross-file transaction and garbage-collection problems.

### Rejected: Markdown frontmatter as canonical claim storage

Frontmatter is attractive to humans but unreliable as the machine contract here:

- current Markdown styles are inconsistent and frontmatter is only recommended;
- YAML requires a dependency or incomplete custom parser;
- duplicate keys, implicit types, multiline statements, timestamps, and nested validation results are easy to parse inconsistently;
- prose and generated summaries can drift from frontmatter;
- several claims per page create ambiguous update and merge ownership.

Markdown may include lightweight claim references, but it should not carry canonical derived assessment.

### Rejected: one monolithic JSON/YAML/Markdown claim registry

A single file offers simple enumeration but causes unrelated claim updates and validator refreshes to collide, makes review noisy, and increases corruption blast radius.

### Rejected: NDJSON, TOML, custom text, SQLite, or Git notes

- NDJSON makes nested records hard to review and causes whole-line conflicts.
- TOML and YAML need new parsing support and do not improve the nested model enough.
- a custom format creates parser and tooling debt.
- SQLite is not naturally Git-diffable and violates the no-database requirement.
- Git notes are less visible, harder for agents and humans to edit, and not present in ordinary clones by default.

### 10.1 Implemented claim revision and compare-and-swap model

Claim revisions are transport/store metadata, not canonical claim fields. A read computes an opaque `sha256:<full-hex-digest>` token over the exact bytes of the strict canonical claim file. `created_at` and `updated_at` remain domain timestamps and are never concurrency tokens. Create, get, list, and every successful mutation return the corresponding revision; a no-op mutation returns the unchanged revision and does not rewrite the file or advance `updated_at`.

Every mutation other than exclusive creation requires the revision previously returned to the caller. The claim store acquires the claim's cross-process lock, re-reads and fingerprints the current bytes, compares the token, applies the mutation only to that exact state, validates and deterministically serializes the whole aggregate, checks the current bytes again, atomically replaces the file, and returns the new revision. A mismatch returns a typed conflict containing the expected and current opaque tokens. Scrinium does not merge stale writes and does not use last-write-wins because either behavior could silently discard evidence, lifecycle changes, policy changes, or validation history.

Claim creation uses atomic exclusive publication and refuses an existing ID. All canonical mutations—meaning-preserving edits, evidence attachment, validation-policy changes, validation-result recording, supersession, and withdrawal—use the same store-owned compare-and-swap path. Revision calculation is not duplicated in application services or validator adapters, and revision tokens are not written into claim JSON or linted as project knowledge.

Cross-process mutation locks are per claim at `llm-wiki/.scrinium/locks/claims/<CLAIM-ID>.lock`, with the runtime directory ignored by Git and excluded from wiki document listing. Scrinium opens a non-linked regular lock file and uses an advisory operating-system file lock. The kernel releases ownership when a process exits; the reusable lock file is deliberately retained, so a crashed writer leaves no ownership to steal and removing/replacing a lock inode cannot split coordination. Waiting observes context cancellation and deadlines. Different claims do not share a global mutation lock.

Validation follows read/execute/CAS semantics. The application reads the claim and revision, verifies the caller's expected revision, releases all claim locks, builds the repository input, and runs the validator. Persistence later attempts one compare-and-swap with the original revision. If any claim byte changed while Rulefloor, Gograph, manual, or a future validator ran, the result is rejected as stale input with a typed claim conflict and is not appended to the newer aggregate. Required-binding orchestration advances its expected revision after each successfully persisted result. Concurrent results from the same starting revision do not silently merge: one may commit and the other must be explicitly retried from the new state.

This coordination covers Scrinium processes using the claim store. A direct filesystem writer does not participate in the advisory lock; the exact-byte recheck detects changes made before the final CAS check, but Scrinium does not claim to sandbox arbitrary filesystem mutation.

### 10.4 Canonical source records (implemented)

Canonical source metadata uses one strict `scrinium.source/v1` JSON record per immutable source ID at `llm-wiki/sources/records/<SOURCE-ID>.json`. The record separates closed source type, producer origin, provenance trust classification, raw repository path, exact raw-byte SHA-256, lifecycle, and derived claim/page references. Origin/trust describes provenance suitability; it is never a claim assessment or proof of implementation behavior.

Source reads return an opaque SHA-256 revision of the exact canonical bytes. Mutations require that observed revision and run under a per-source cross-process lock in the ignored runtime lock tree. Creation is exclusive, IDs cannot be renamed, no-op writes preserve the revision, and stale writers receive typed conflicts. Source records use strict decoding, duplicate-key rejection, closed enums, deterministic field order, two-space indentation, final newline, regular-file enforcement, symlink rejection, compare-before-write, and atomic replacement.

Repository-local raw sources must exist as confined non-linked regular files when registered. Scrinium stores their full SHA-256 fingerprint but never silently changes it. Missing or changed bytes produce deterministic lint and source-evidence freshness findings until an explicit CAS-protected refresh accepts the new bytes. A fingerprint identifies bytes, not the semantic correctness of those bytes.

`source-registry.md` is now a deterministic generated compatibility view and `sources/<SOURCE-ID>.md` remains a human-authored/agent-authored summary. Neither is canonical source state. Read-only migration parses only known Scrinium registry/summary structures, reports ambiguity or missing inputs as debt, and creates nothing. Explicit apply exclusively creates safe JSON candidates, is idempotent, and does not rewrite or delete legacy Markdown; registry regeneration is a separate explicit operation.

Claim evidence may use `source:<SOURCE-ID>` or an exact source ID as a canonical source locator. Application views and deterministic lint resolve the source record and current raw bytes, then feed availability and observed fingerprints into the existing derived-state engine. Withdrawn, missing, unreadable, or byte-changed sources degrade through existing freshness rules; provenance alone never produces machine verification.

## 11. Session model decision

The single implicit in-memory session has been replaced with explicit durable
tracked work-session checklist records.

- `begin_session` returns a unique session ID.
- CLI operations accept `--session <id>`; an environment variable may be a convenience but not the only linkage.
- an MCP stdio connection may retain its current session ID as adapter context, while the underlying state is persisted so restart and CLI continuation are possible;
- strict deterministic `scrinium.session.v1` files live at
  `llm-wiki/.scrinium/sessions/<session-id>.json`; the whole
  `llm-wiki/.scrinium/` runtime area is Git-ignored because it is operational
  coordination state, not canonical project knowledge;
- each record includes repository identity, creation/update times, read/write observations, and status;
- beginning another session does not erase an existing one;
- sessions transition explicitly from `active` to `finished` or
  `abandoned`; closed sessions reject later tracking and writes, active
  sessions can be listed, and no stale session is automatically deleted,
  finished, or abandoned;
- `finish_session` validates only Scrinium-observed obligations and must say so. It cannot guarantee that external project edits were documented or that an agent followed instructions.

The knowledge store remains repository-owned and Git-diffable; ephemeral session coordination is local repository state but intentionally not committed. No daemon or database is required. Cross-process locking and explicit IDs are necessary acceptance criteria, not later refinements.

The phrase “enforced session loop” should be deprecated in favor of “tracked work-session checklist” unless Scrinium gains an integration that can actually observe all scoped project changes.

Implemented concurrency model:

- IDs are opaque `ses_` identifiers backed by 128 bits from
  `crypto/rand`; they are coordination identifiers, not authentication
  credentials and never become path components until strict validation passes.
- Each mutation takes an advisory per-session lock at
  `llm-wiki/.scrinium/locks/sessions/<session-id>.lock`, re-reads and strictly
  validates the current regular JSON file, unions the newly observed state,
  and atomically replaces the record. Concurrent processes therefore cannot
  lose read/write tracking or maintenance obligations. Retained lock files are
  harmless ownership points; file-lock ownership ends when the descriptor or
  process closes, so no automatic lock stealing or stale-artifact deletion is
  required.
- Lock acquisition polls with the caller's context. Cancellation and deadline
  expiry return typed operational session errors. Runtime record and lock
  directories and files reject symlinks and non-regular record files.
- Application requests carry an explicit session ID. An MCP adapter may retain
  the ID returned by `begin_session` as connection context, while
  `continue_session` restores that convenience after restart. Direct CLI
  operations use `--session <id>`.
- Short project mutations and their tracking update occur while the session
  lock is held, so a concurrent finish cannot admit an untracked write.
  External validator execution never holds a session lock. Validation first
  checks the observed active session, executes externally, and then must
  reacquire the session lock for claim-CAS persistence. If the session closed
  or the claim revision changed meanwhile, the result is rejected instead of
  being attached to an obsolete state.
- `finish_session` leaves the record active when required reads or observed
  maintenance remain pending. `abandon_session` requires a reason and remains
  distinguishable from successful completion. Session files retain no derived
  knowledge or validation results.
- Last-write-wins is rejected because it can erase concurrent observations and
  validation-history bookkeeping. Scrinium still cannot observe direct
  filesystem changes or actions outside its interfaces; the durable record is
  a checklist of observed operations, not a security boundary or proof of
  agent compliance.

## 12. Deterministic lint versus heuristic lint

v0.2 must produce two visibly distinct report sections and machine-readable `analysis_kind` values.

### Deterministic integrity lint

These checks can justify definitive findings:

- claim JSON parses under a supported schema;
- filename and claim ID match, and IDs are unique including case-folded filesystems;
- required fields, enums, timestamps, and lifecycle links are valid;
- every evidence and claim reference resolves to an allowed target;
- repository paths are confined, regular, and match recorded fingerprints when a fingerprint is required;
- validation bindings name registered validators and supported binding versions;
- result fingerprints and binding IDs are internally consistent;
- required validation is missing, expired, failed, or cannot be evaluated;
- a `superseded` claim names a present successor and successor links are acyclic;
- generated indexes/views match canonical records, if such views are enabled;
- required guidance paths exist and agree with the canonical startup-page list;

Deterministic lint may derive stale status from explicit expiry, digest, revision, or missing-reference rules. It must not infer semantic staleness from prose dates.

### Heuristic review lint

These can only produce review leads with method and limitations:

- possible natural-language contradiction or duplicate;
- prose that may describe obsolete behavior without an explicit freshness policy;
- instruction-like language in untrusted or source-derived material;
- a page that appears topically orphaned or insufficiently linked;
- likely claim candidates found in legacy Markdown.

Heuristics must never set `verified`, `challenged`, `stale`, `superseded`, or `withdrawn`. Prompt-injection analysis should be scoped to untrusted/derived content, recognize quoted/example regions where practical, and never be described as detection or prevention. The current six-phrase scan may be retained temporarily only as a named low-confidence heuristic with false-positive tests.

## 13. Gograph integration boundary

The Gograph adapter is implemented under `internal/integrations/gograph/`. It implements the generic validator interface through a subprocess boundary and imports no Gograph packages. The generic binding uses `gograph.binding.v1`: `reference` is the exact subject `SymbolNode.ID` or package import path; `parameters.predicate` is one of `symbol_exists`, `package_imports`, `call_edge_exists`, or `type_implements`; `parameters.required_precision` is `ast` or `precise`; and `parameters.object` is required only for relationship predicates. Reference kind and Go language are derived from the predicate. No binding can supply an executable, repository path, file path, query language, arbitrary flag, reachability expression, command, or shell fragment.

The application configuration may select the trusted executable through `validators.gograph.executable`; the default is `gograph` through ordinary `PATH` resolution. Startup continues when version discovery or executable resolution fails. In that case the validator is absent from the registry and an attempted bound validation degrades to `cannot_evaluate` through generic orchestration.

The adapter uses only `gograph version --json` (`gograph.version.v1`) and `gograph validate --repo PATH --binding-json JSON --json` (`gograph.validation.v1`). It strictly checks duplicate and unknown JSON fields, Gograph version stability, the echoed canonical binding and binding fingerprint, exact repository root, source/build/graph fingerprints, analysis mode, precision, completeness, freshness, timestamps, evidence identities, relationship classifications, and the outcome/exit-code pair. It independently hashes the confined regular `.gograph/graph.json` artifact when Gograph returns a graph fingerprint. It does not reproduce Gograph's source-selection algorithm; the Gograph source fingerprint is retained alongside Scrinium's independent repository snapshot and input fingerprints.

Implemented assurance and guarantee:

- Every Gograph result is capped at observation assurance. A structural pass cannot satisfy a verification-grade binding or produce machine-verified presentation by itself.
- A pass means the selected structural predicate was established against the recorded current Gograph graph and selected Go repository/build context.
- A fail means Gograph reported evaluated absence under its predicate-specific completeness rules. Symbol/import absence requires complete AST-or-better analysis; implementation absence requires precise-complete analysis; and call-edge absence requires complete call resolution.
- Missing or stale graphs, repository mismatch, insufficient precision, partial or unresolved analysis, malformed or inconsistent output, unavailable executables, timeout, and cancellation remain `cannot_evaluate`. The adapter never invokes `gograph build` or silently refreshes graph state.
- Result history retains Gograph version, predicate and exact identities, source/graph/binding/build-context fingerprints, analysis mode, precision, completeness, freshness, reason code, concise source locations, relationship classification, Scrinium repository/input fingerprints, and bounded diagnostics.

CHA call evidence is recorded as `cha_possible_target`, meaning a possible static target rather than runtime dispatch certainty. Gograph v1 supports Go structure only and excludes reachability. For `LoginService -> LocalCredentialProvider`, Gograph can support a structural relationship claim; it cannot alone establish that administrators always retain usable local authentication at runtime or that surrounding business behavior is correct.

The core knows only validator ID, binding version/reference, result, assurance ceiling, fingerprints, and evidence. It imports no Gograph types and encodes no Gograph command behavior in `knowledge.Claim`.

## 14. Rulefloor integration boundary

The Rulefloor adapter is implemented under `internal/integrations/rulefloor/`. It implements the generic validator interface through a subprocess boundary and imports no Rulefloor packages. The adapter accepts `rulefloor.binding.v1`: the generic binding `reference` is the Rulefloor rule ID, `parameters.mode` is `static` or `execute`, and optional `parameters.profile` is allowed only for execute mode. No binding can supply an executable, repository path, build tag, arbitrary flag, command, or shell fragment.

The application configuration may select the trusted executable through `validators.rulefloor.executable`; the default is `rulefloor` through ordinary `PATH` resolution. Startup continues when version discovery or executable resolution fails. In that case the validator is absent from the registry and an attempted bound validation degrades to `cannot_evaluate` through the generic orchestration path.

The adapter uses only `rulefloor version --json` (`rulefloor.version.v1`) and single-rule `rulefloor validate ... --json` (`rulefloor.validation.v1`). It checks the selected rule, mode/profile, exact resolved repository root, ledger path and SHA-256 against repository bytes, Rulefloor version, timestamps, closed outcomes/statuses, test/proof fingerprint shapes, execution state, and the outcome/exit-code pair. Timeout, cancellation, missing executables, malformed or unsupported JSON, repository mismatch, and inconsistent process results become `cannot_evaluate`; infrastructure errors are never converted into a selected-rule failure.

Implemented assurance and guarantee:

- A Rulefloor static pass means the selected rule's binding and test integrity matched the recorded ledger state. It is observation-grade because no test executed.
- A Rulefloor execute pass means Rulefloor actually executed the selected supported rule successfully under the recorded mode/profile and repository snapshot. Verification grade additionally requires authentic execution-requested, execution-performed, execution-pass, repository, and input-fingerprint fields.
- An evaluated selected-rule failure maps to `fail`. A static integrity failure remains observation-grade; a performed executable failure may be verification-grade evidence of failure.
- A Rulefloor `cannot_evaluate`, or any adapter inability to authenticate a result, remains `cannot_evaluate` and cannot preserve current verified presentation.
- The result retains concise structured diagnostics plus Rulefloor version, rule/mode/profile, ledger fingerprint, expected/actual test fingerprints, proof fingerprint when present, Rulefloor reason, execution state, repository fingerprint, and Scrinium input fingerprint. Large stdout, stderr, and test logs are not stored in claim history.

Neither static nor execute success means unrelated project behavior is correct. A Rulefloor result covers only the selected rule under the recorded execution model; it does not prove adjacent requirements, production deployment state, or the correctness of the natural-language mapping. That mapping remains explicit and reviewable in the validation binding.

## 15. Backward-compatibility strategy

Backward compatibility is transitional, not a reason to preserve Page as the knowledge abstraction.

### Preserve

- local filesystem storage and ordinary Git review;
- stdio MCP operation and single-binary deployment;
- read-only listing/reading of existing Markdown;
- source IDs, raw-source provenance, and the rule that source content is evidence rather than instruction;
- protected path patterns and semantic denial messages, after hardening;
- create-only page behavior, non-overwriting moves, archive-over-delete, and atomic single-file replacement;
- `capabilities` as the honest description of live features;
- managed instruction blocks, content preservation, dry-run, and check behavior;
- current Makefile verification pipeline.

### Deprecate or rename

- `Page` as the central knowledge concept; page APIs become document compatibility APIs;
- `update_wiki_page` as the preferred way to change project knowledge; claims use typed claim commands/services;
- `lint_llm_wiki` in favor of knowledge integrity lint plus explicitly heuristic document review; keep an alias during transition;
- `adopt_llm_wiki` in favor of a migration assessment that emits candidates and a report;
- `enforce-agents` in favor of `sync-agent-instructions`; keep a compatibility alias for a documented period;
- “source of truth,” “reduces/prevents hallucinations,” “detects contradictions,” “detects stale claims,” and “enforced session loop” claims unless later implementation evidence supports them.

### Make internal implementation detail

- MCP content maps and JSON-RPC error mapping;
- default Markdown templates;
- filesystem path resolution and atomic-write mechanics;
- source registry Markdown parsing during compatibility import;
- derived assessment and `last_validated` rendering.

### Remove after migration, not immediately

- the implicit singleton session;
- arbitrary append bypass for every directory-pattern-protected path;
- caller-authored status labels that can say `verified` without validation policy;
- semantic promises in generated instructions that storage cannot enforce;
- naive substring source-registry mutation once typed source import/export exists.

### Existing data migration

Existing Markdown remains usable and unchanged by default. Automatic migration may safely extract:

- page path, frontmatter type/status/update date when syntactically recognized;
- source IDs and exact registry fields from known Scrinium-generated entries;
- explicit ADR/decision IDs and repository locators;
- explicit claim IDs already present in a supported form;
- provenance links between source summaries and raw paths, with availability/fingerprint findings.

Automatic migration must not promote arbitrary prose bullets or summaries into verified claims. It may emit deterministic `claim_candidates` with source location and `asserted` as the maximum proposed assessment; an owner or authorized workflow must approve IDs, statement boundaries, evidence polarity, and validation policy before canonical claim files are created.

Migration should be additive and idempotent. It writes a report first, supports dry-run, never rewrites existing Markdown, never deletes legacy data, and records exactly which canonical claim files would be created. Rollback is removal of newly created claim records before subsequent edits; no source page restoration should be necessary.

The current `source-registry.md` will remain a temporary compatibility and human-readable view in v0.2. Canonical source metadata will use one deterministic JSON file per source. The importer should parse only the known generated Markdown structure and report unparsed sections. Claim evidence locators must continue to work while both representations coexist.

## 17. Risks

- **False precision:** A richer schema can look authoritative. Mitigation: derived state, scoped wording, no numeric confidence, and prominent evidence gaps.
- **Natural-language scope mismatch:** A binding may verify only part of a broad statement. Mitigation: require atomic statements and explicit binding scope; reject verification when scope is incomplete.
- **Validator over-trust:** Tool output may be stale, incomplete, or compromised. Mitigation: assurance ceilings, version/revision/fingerprint capture, confined execution, and cannot-evaluate fallback.
- **Merge churn:** Automatic validations can update many files. Mitigation: one claim per file, compare-before-write, explicit batch review, and a defined result-retention policy.
- **Repository noise from sessions:** Durable sessions could pollute Git. Mitigation: keep runtime session records repository-local but ignored; keep claims/evidence committed.
- **Legacy ambiguity:** Markdown prose cannot always be segmented into stable claims. Mitigation: candidate reports, no automatic confidence, owner approval for ambiguous promotion.
- **Compatibility drag:** Keeping generic page writes indefinitely would preserve the bad abstraction. Mitigation: explicit document-only classification and a dated removal decision.
- **Partial multi-file operations:** source metadata, summaries, views, and indexes can diverge. Mitigation: canonical source JSON is written first; summaries and registry/index views remain rebuildable compatibility outputs. A canonical create may therefore survive a later view-write failure and must be reconciled explicitly rather than rolled back silently.
- **Filesystem races:** preflight path checks alone are not a complete local adversary boundary. Mitigation: rooted store abstraction, locks, repeated checks at mutation, strict file types, and honest threat-model documentation.
- **Claim ID ownership:** human-readable semantic IDs require deliberate allocation and can be awkward when a statement changes. Mitigation: IDs are immutable; a material meaning change creates a successor claim that explicitly supersedes the old claim. Claim renaming is not supported.
- **Manual verification ambiguity:** users may read a careful manual check as equivalent to executable verification. Mitigation: manual verification is observation-grade only and can never produce machine-verified status.

## 18. Explicit acceptance criteria for v0.2

v0.2 is acceptable only when all of the following are true:

1. A typed claim record exists independently of Markdown pages and is stored as one deterministic JSON file per claim.
2. Existing Markdown remains readable without migration and no migration rewrites or deletes it.
3. Claim lifecycle, assessment, freshness, and validation outcomes are separate and covered by table-driven tests.
4. A stored claim with no independent evidence displays as asserted, never sourced or verified.
5. A source summary cannot be evidence for its own generated statements; provenance-cycle and same-origin tests enforce this.
6. A claim with only documentary evidence cannot display as verified.
7. Verification requires an explicit policy and current passes for every required verification-grade binding.
8. Missing validator, missing evidence, changed fingerprint, stale repository snapshot, timeout, cancellation, and unsupported binding produce `cannot_evaluate` and remove current-verified presentation.
9. Failed required validation produces challenged assessment with the failing binding visible; it is not silently rewritten or superseded.
10. The generic validator interface is usable by fake and manual validators without importing Gograph or Rulefloor internals into the core.
11. No Gograph or Rulefloor integration is required for Scrinium to operate, read claims, lint integrity, or record manual evidence.
12. MCP and CLI are adapters over typed application services; domain operations do not return MCP `map[string]any` values.
13. Separate CLI processes can begin, continue, inspect, and finish one explicit session, with concurrency tests.
14. Session output states that it checks only Scrinium-observed actions and does not claim full agent compliance.
15. Repository root, wiki root, claim paths, evidence paths, and session paths have deterministic confinement, regular-file, symlink, malformed-pattern, and concurrent-writer tests.
16. Source import validates IDs, enumerated origin metadata, dates, repository-relative raw paths, existence/type when claimed, and content fingerprints when available.
17. Deterministic lint and heuristic review are separate in API and human output; heuristic findings cannot change claim state.
18. Scrinium does not advertise semantic contradiction/staleness or prompt-injection detection unless the exact implemented check justifies that wording.
19. Managed agent instructions no longer call stored Markdown a source of truth or claim to enforce behavior they cannot observe.
20. Pull-request CI runs `make verify`, and tests cover the stdio MCP boundary, cross-process CLI sessions, migration fixtures, state degradation, and validator failures.
21. `make verify` passes with build, tests, vet, format check, staticcheck, govulncheck, and tidy check.
22. A migration dry-run over the current repository produces no Markdown modifications, no verified claims, and an explicit report of ambiguous claim candidates and missing or conflicting required guidance paths.

Implementation note: criteria 1–21 are exercised by the repository verification suite. Criterion 22 remains data-dependent: the dry-run mechanism is non-mutating and reports debt, but owner review is still required for ambiguous current-repository prose. Acceptance of the protected architecture overview is also intentionally outside automatic implementation because that file is governed.

## What Scrinium is NOT

- Scrinium is not a truth oracle.
- Scrinium is not a guarantee that stored Markdown or JSON is correct.
- Scrinium is not a hallucination prevention system.
- Scrinium is not a semantic contradiction detector.
- Scrinium is not a general stale-prose detector.
- Scrinium is not a prompt-injection prevention or detection guarantee; any content scan is heuristic unless narrowly specified otherwise.
- Scrinium is not a replacement for source code, tests, ADRs, Gograph, Rulefloor, Git, or human judgment.
- Scrinium is not a database, mandatory daemon, cloud service, or hosted authority.
- Scrinium is not an agent sandbox and cannot enforce actions performed outside its interfaces.
- Scrinium is not entitled to preserve confidence when evidence cannot be checked.

Its bounded responsibility is to keep a durable, inspectable record of what the project claims, why those claims are held, what validation was attempted, what the results covered, and where uncertainty remains.

## Fixed owner decisions

1. **Claim IDs:** use human-readable semantic IDs. IDs are immutable, claim renaming is unsupported, and a material meaning change requires a new claim that supersedes the old claim.
2. **Manual verification:** manual verification is observation-grade only and can never produce machine-verified status.
3. **Source metadata:** canonical v0.2 source metadata will use one deterministic JSON file per source. `source-registry.md` remains temporarily as a compatibility and human-readable view.
4. **Compatibility:** existing page tools and `enforce-agents` remain available throughout v0.2 as deprecated compatibility interfaces; they are not removed during v0.2.
5. **Validation history:** v0.2 keeps complete validation history in each claim record. Retention and archival policy are deferred.

## Deferred to v0.3

- background or repository-wide validation scheduling;
- automatic stale-session cleanup;
- validation-history retention, archival, or compaction;
- automatic knowledge refresh or semantic contradiction detection;
- removal dates for deprecated v0.1 page/wiki and `enforce-agents` compatibility interfaces.
